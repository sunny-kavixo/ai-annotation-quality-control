# V0.3 — label quality and dataset-level signals

V0.1 established structural annotation validation. V0.2 made bounding-box checks image-aware. The next practical gap is label quality.

A dataset can be geometrically valid while still containing taxonomy problems such as `car`, `Car`, and ` car `, or labels that are not part of the project's approved class list.

## First V0.3 slice

This milestone starts with a separate label-quality inspection module. It:

- normalizes labels for analysis without silently rewriting source data;
- reports inconsistent formatting as a warning;
- optionally validates labels against an allowed taxonomy;
- produces normalized class counts for later QC reporting/dashboard work.

The exercise dataset deliberately includes formatting variants and an out-of-taxonomy `forklift` label.

## Why this is separate from the core validator

The allowed taxonomy is project-specific. Hard-coding a global class list into structural validation would make the QC engine less reusable. V0.3 therefore keeps taxonomy inspection explicit while we exercise the API and decide how project configuration should be supplied.

## Not implemented yet

No class-imbalance threshold is claimed yet. A rare class is not automatically bad data, so we should not invent a universal imbalance rule before defining a defensible project-level policy.
